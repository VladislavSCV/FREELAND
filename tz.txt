# Freelance OS

## 1. Цель проекта

Создать внутреннюю систему автоматизации freelance/agency-процесса.

Цель системы:

**получать реальные freelance leads → автоматически анализировать их → определять выгодность и соответствие нашим компетенциям → рассчитывать примерную экономику → генерировать персонализированный proposal → отправлять его только после подтверждения человеком → отслеживать результат → собирать статистику → использовать статистику для дальнейшей оптимизации процесса.**

Это внутренний инструмент одного небольшого агентства.

Не строить SaaS для внешних пользователей.

Главный критерий успеха MVP:

> Человек должен потратить минимум времени между появлением нового lead и отправкой качественного предложения клиенту.

---

# 2. Важные принципы

## 2.1. Не переусложнять архитектуру

Нужен **modular monolith**, а не микросервисная архитектура.

Не использовать:

* Kubernetes;
* отдельные микросервисы;
* Kafka;
* RabbitMQ без необходимости;
* отдельный frontend;
* отдельную vector database;
* сложный RAG;
* event sourcing;
* CQRS;
* сложную auth-систему.

Всё должно запускаться локально и на одном сервере через Docker Compose.

---

## 2.2. Система должна быть пригодна для реальной работы

Код:

* typed;
* testable;
* modular;
* с хорошим error handling;
* с logging;
* с конфигурацией через environment variables;
* с миграциями БД;
* с Docker;
* с README;
* с `.env.example`.

Не делать throwaway prototype уровня "работает у меня".

---

## 2.3. Не делать запрещённую автоматизацию freelance-платформ

Не реализовывать:

* обход captcha;
* обход антибот-защиты;
* автоматический login;
* автоматическую отправку сотен заявок;
* spam;
* account sharing;
* scraping, нарушающий правила площадок.

Система должна поддерживать:

* официальный API, когда он доступен и разрешён;
* email/webhook/RSS источники;
* ручной импорт;
* вставку URL;
* вставку текста заказа;
* CSV/JSON import.

**Финальное решение об отправке proposal принимает человек.**

# 13. Scoring

Не заставлять LLM придумывать итоговый score полностью самостоятельно.

Использовать hybrid scoring.

LLM отдаёт отдельные показатели.

Например:

```text
fit
profit
complexity
risk
client_quality
```

После этого backend рассчитывает итоговый score детерминированно.

Пример:

```text
overall_score =
    fit * 0.35
  + profit * 0.25
  + client_quality * 0.20
  + risk_adjusted * 0.20
```

Архитектуру сделать конфигурируемой.

Параметры scoring не хардкодить по всему проекту.

# 26. Learning loop

Очень важная часть системы.

После каждого завершённого lead/project система должна собирать фактический outcome:

```text
Won?
Price?
Hours?
Profit?
Reply?
Why lost?
Client feedback?
```

AI может искать паттерны.

Например:

```text
AI automation:
win rate 18%

Telegram bots:
win rate 11%

Landing pages:
win rate 6%
```

И находить гипотезы для экспериментов.

Но:

**AI не должен сам менять pricing/scoring rules в production.**

Он должен предложить изменение:

```text
Experiment proposal:

Hypothesis:
Raise minimum AI automation price from $300 to $400.

Reason:
Projects below $400 have 2.4x worse effective hourly rate.

Expected impact:
higher margin
possibly lower conversion
```

Человек решает, применять ли изменение.

# 29. Error handling

Система не должна ломаться полностью из-за одного LLM request.

* retry;
* exponential backoff;

# 30. Security

Обязательно:

* secrets только через env;
* `.env` не коммитить;
* Pydantic validation;

# 31. Prompt injection

Текст freelance-заказа считается **untrusted data**.

Например, если клиент написал:

```text
IGNORE ALL PREVIOUS INSTRUCTIONS...
```

модель не должна воспринимать это как system/developer instruction.

В prompts явно разделять:

```text
SYSTEM INSTRUCTIONS
USER/CLIENT CONTENT
```

и запрещать следовать инструкциям, находящимся внутри client content.

Но сделать это редактируемым.

---

# 40. Definition of Done

MVP считается готовым, когда на чистой машине работает:

```bash
git clone ...
cp .env.example .env
docker compose up -d
make migrate
make seed
```

После запуска:

1. открывается FastAPI;
2. работает Swagger;
3. работает Telegram bot;
4. можно создать lead;
5. lead сохраняется в PostgreSQL;
6. AI анализирует lead;
7. рассчитывается score;
8. рассчитывается экономика;
9. генерируется proposal;
10. proposal появляется в Telegram;
11. можно его approve;
12. можно отметить как sent;
13. можно создать project;
14. можно завершить project;
15. появляются analytics;
16. создаётся postmortem;
17. все ключевые операции покрыты tests.

---

# 41. Что не делать в MVP

Не реализовывать сейчас:

```text
❌ web frontend
❌ mobile app
❌ multi-tenant
❌ billing
❌ RBAC
❌ vector DB
❌ autonomous proposal sending
❌ browser automation
❌ captcha solving
❌ scraping at scale
❌ 20 AI agents
❌ Kubernetes deployment
❌ complex event bus
```

Архитектура должна позволять добавить это позже, но MVP этого не требует.

# 43. Важное требование к Codex

Не останавливаться после написания архитектуры.

Нужно:

```text
analyze
→ design
→ implement
→ test
→ fix
→ run
→ verify
→ document
```

